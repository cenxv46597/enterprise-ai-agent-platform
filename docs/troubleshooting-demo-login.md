# 演示客户端登录超时排查

后端显示 Application startup complete，只能说明 API 进程启动；当前 `/health` 也只检查
进程能否响应，没有检查 PostgreSQL。登录需要访问数据库中的用户记录，数据库不可达时
仍可能等待超时。这种超时不能据此判断密码错误。

按下面的顺序检查：

1. 保持后端运行，打开 Docker Desktop，等引擎就绪。
2. 确认本项目已有的 `db` 容器运行且健康，复用原容器和数据卷。
3. 在另一个本机终端重新运行 `browse_demo.py --username demo_a`，隐藏输入已有密码。

如果命令行的 Docker 不支持 `compose`，先用 `Get-Command docker -All` 核对实际调用的
程序。机器上可能同时装有旧版 CLI 与 Docker Desktop 自带 CLI；Docker Desktop 的
终端或自带 CLI 可用于核对引擎和容器。不要把 CLI 不支持命令当作数据库密码问题。

客户端现在区分固定阶段的连接失败、响应超时、其他网络故障及 HTTP 状态错误；不输出
密码、Token、响应全文或原始异常。登录返回 HTTP 401 时才沿账号凭据方向继续检查；
超时则先核对后端日志及数据库可达性，不需要重新注册或分配旧空间。

2026-10-15，本机排查观测为 `/health` 返回 200、匿名 `/auth/me` 返回 401，但使用
不存在的探测账号进行登录，10 秒后 ReadTimeout；本机 PostgreSQL TCP 连接也超时，
Docker Desktop Linux 引擎命名管道不存在。该探测没有使用真实密码或创建账号，
不代表真实账号登录和完整浏览已验收。客户端专项 22 项通过、无跳过（0.49 秒），
全部模拟 HTTP，覆盖连接/超时提示及凭据不回显；未跑日常库 pytest 或调用模型。
