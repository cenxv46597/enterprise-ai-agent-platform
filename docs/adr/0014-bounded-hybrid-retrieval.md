## 背景

现有向量检索已经接通，但错误码、版本号等标识符需要额外验证精确匹配。当前带干扰资料的基线只有四份文档、二十九个文本块，适合先实现能解释和验证的小规模方案。

学习者选择同一文本块在两路命中时合并一条并保留两路排名。这样避免重复占用上下文，仍能解释排序依据；代码与实践由导师完成，独立实现能力尚待验证。

## 方案比较

### Python 词项评分

优点是无需迁移、分词词典或新服务，可逐项检查分词和融合。缺点是每次在应用侧处理完整范围内文本，CPU、内存和数据库传输开销随语料增加，不能直接作为大知识库方案。

### PostgreSQL 全文检索与索引

优点是检索可由数据库索引支持，适合扩大规模。需要明确中文分词和错误码处理、增加索引并验证更新行为；默认配置的行为不应直接当作产品需求。[PostgreSQL 17 官方说明](https://www.postgresql.org/docs/17/textsearch-intro.html)

本机只读检查 `to_tsvector('simple', '访问令牌失效时，返回 TOKEN_EXPIRED。')`，得到整串“访问令牌失效时”以及拆开的 `token`、`expired`。这个具体配置没有提供本轮所需的中文相邻双字和完整下划线错误码行为；不据此推断 PostgreSQL 无法实现中文检索。

当前选择 Python 基线，范围上限为 2000 个可检索块和 100 万原文字符。超过上限拒绝混合请求，不静默选取前半库。默认请求仍采用向量策略，方便保留比较基线。

## 词项与融合决策

- 评分时做全半角与大小写归一化；原文、来源和字符位置保持原样。
- 中文连续片段取相邻双字，英文、数字及错误码保留完整词项；单个汉字不进入词项通道。当前没有词典、同义词、停用词或词干规则。
- 使用 BM25 基线，包含稀有词权重、词频饱和及长度归一化，参数固定为 `k1=1.2`、`b=0.75`。语料单位是文本块，重叠块仍可能产生相近内容。
- 向量与词项各独立选前二十个候选，再按块 UUID 合并，融合后返回请求的前 K 个。词项候选来自完整范围内语料，能够补入未进入向量前二十的块。
- 使用倒数名次融合，每路贡献 `1/(60+名次)`；缺席通道不贡献分数。避免把余弦距离与词项原始分数直接相加。常数 60 是起始选择，没有在本项目中调优。[原始融合论文](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf)
- 同分按块 UUID 稳定排序，通道内重复 ID 不增加票数。块 ID 不同的重叠内容尚未做语义去重。

## 范围与事务

两个短事务保留知识库归属、模型身份与共享锁检查，问题向量请求仍在事务外。第一个事务用有界子查询检查混合处理量，避免为已超限输入请求向量；第二个事务重新检查，模型等待期间增长到超限仍拒绝。

第二个事务通过一次范围内查询取得两路所需的文本及余弦距离，保持同一候选快照。SQL 同时限定工作空间、知识库、`ready` 和非空向量；流式读取最多 2001 行，并在读取中复核正文字符数。全部候选距离必须有效。

词项通道当前也只处理已具备可检索向量的就绪块。向量服务故障沿用现有错误处理，不自动改成仅词项回答。

## 接口与兼容

`/search` 和 `/answers` 请求新增 `strategy`，接受 `vector`、`hybrid`，默认 `vector`。检索响应新增策略与可选融合字段；原 `distance` 始终表示余弦距离。

混合响应 `metric` 为 `reciprocal_rank_fusion`，按 `fusion_score` 降序，不保证距离升序；`vector_rank`、`lexical_rank` 表示各路前二十候选中的名次，缺席记空。分数都不是答案正确率。

回答接口复用融合后的顺序、完整块预算和逐字引用校验，返回答案的结构保持现有契约。混合处理量超限返回 `422`，参数、模型及数据错误沿用现有约定。无需数据库迁移、新依赖或重新向量化。

## 验证与限制

受控数据库用例让正确错误码块在向量排序中位于第 21 名，验证词项独立补入并在最终结果排第 2 名，且只返回一次。其他用例覆盖范围过滤、字符与块数上限、等待期间增长、事务外模型调用、模型身份变化、无效向量以及融合后引用位置。

历史六题前十候选的[离线排序回放](../evaluation/hybrid-ranking-replay-2026-10-11.json)，两种排序的前五均覆盖五条必需证据。词项评分也仅使用这些十候选；这个结果没有执行全库独立词项召回，不能替代正式混合接口的真实效果验收。两道负例不计覆盖成绩，本轮没有生成答案。

双字匹配可能带来主题相近的噪声，名次融合可能降低某些语义结果排名。保留默认向量基线，后续通过更丰富问题验证，再决定是否启用混合默认和引入重排。达到规模上限或出现具体延迟瓶颈时重新评估索引方案。
