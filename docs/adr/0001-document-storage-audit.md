# ADR 0001：文档文件与数据库先采用只读对账

- 日期：2026-10-09
- 状态：已采用；本次实现范围为检测，补偿操作待后续设计。

## 背景

文档入库先保存原文件，再提交 PostgreSQL 元数据。文件系统和数据库没有共同事务。普通异常可触发代码补偿；进程在保存成功后、首次提交前退出时，会留下没有记录的文件。数据库记录存在但文件丢失也是需要发现的异常。

文件路径只包含 UUID。原文件名、媒体类型和知识库归属没有独立保存在磁盘上，因此不能从孤儿文件可靠重建完整文档记录。

## 比较的方案

1. **先持久化上传意图，再保存文件。** 可保留归属信息并驱动恢复，但会产生有意图而没有文件的情况；需要新增状态、修改文件大小和摘要约束，或新增意图表，并实现恢复状态机。
2. **保留当前同步入库流程，增加对账。** 复用 Python、SQLAlchemy 和本地文件存储即可识别异常，不新增服务或数据库结构；无法自动恢复丢失的归属信息，需要用户重传或人工核查。

## 决策

当前是小规模、本地单用户、同步上传项目，先采用第二种方案。维护人员运行独立命令，读取全部文档存储键和存储目录的已发布文件，以 JSON 输出三类结果：

- `orphan_candidates`：没有记录且超过宽限期的文件，默认宽限期一小时。
- `recent_untracked`：没有记录但仍在宽限期内的文件，可能正在上传。
- `missing_files`：数据库引用、磁盘未发现的文件。任何状态的文档都参与对账，解析失败不等于文件应删除。

命令只读，不自动补录、删除或修改状态；不会读取文档内容。只检查服务生成的最终文件名，临时文件和未知命名不在本次对账范围内。数据库不可读、存储目录不存在或扫描失败时返回错误，不能把读取失败解释为数据库空表。

## 代价与边界

数据库查询与目录扫描不是同一时刻的原子快照。宽限期只能降低误报，不能证明一个上传已结束；修改时间也不是业务完成时间。报告用于排查，不能直接作为删除依据。本地维护时宜停止上传后再核查，重复扫描并重新确认数据库引用。

本次不检测内容损坏、长期停留的 `uploaded` / `processing` 状态，也不恢复上传或清理临时文件。内存使用随文档数量增长，当前实现适用于小规模；数据量增长后再采用分页和批量对账。

## 验证

故障注入测试在文件保存成功后、首次数据库提交前抛出 `SystemExit`，模拟无法执行 `Exception` 补偿的退出窗口。验证孤儿文件可被报告，宽限期边界准确，已有引用被保留，重复扫描不改变文件，错误配置不创建空目录。另有 PostgreSQL 集成测试核对真实数据库查询。

2026-10-09 本地验证：20 项测试通过、26 项 PostgreSQL 集成测试跳过；Docker 数据库服务未运行，且未配置 `EAAP_TEST_DATABASE_URL`。本次不能据此宣称真实数据库对账已通过验证。

2026-10-10 补充验证：恢复本项目 PostgreSQL 容器，真实数据库下全部 52 项测试通过、无跳过，包含对账集成测试。修正了客户端先转义换行文件名造成的测试输入假设，并新增原始控制字符请求与入库服务验证；临时空数据库迁移与模型一致性检查通过。

## 重新评估条件

业务明确要求恢复每一次已接收上传、入库变为异步任务、开始多进程部署，或出现必须自动补偿的积压时，再设计持久化上传意图、幂等重试和状态恢复；增加自动清理前必须解决并发上传与扫描的竞争窗口。
