# ADR 0021：受控的标准月费加上门次费估算

- 日期：2026-10-11
- 状态：已采用；程序验证、模拟模型与真实模型语义验收分别记录。

## 背景与方案比较

阶段 4.1 能把“三次”绑定到正在等待的 visit_count，阶段 4.2 能让已确认用户数值
参与来源绑定算术。但“数字来源正确、乘法结果正确”仍不等于“业务费用问题已解决”。
还需要明确计费月份、两种费率的单位、公式结构及规则是否适用。

方案 A：模型提出自由公式，程序再验证单位、业务条件和公式。
表达能力强，能够扩展套餐、折扣、税费等情形；但必须建设通用表达式、单位与政策
验证机制。只检查来源或算术，无法证明模型选择了正确业务公式，当前规模难以充分验收。

方案 B：程序提供一个固定且有版本的业务流程，模型仅找到适用的完整标准收费原文。
程序绑定费率与角色，收集两个明确条件，再执行
`月费 × 计费月数 + 每次上门服务费 × 上门次数`。
范围较窄，但可以逐条验证输入、来源、单位、步骤和完成条件，不需要引入通用公式引擎。

本轮采用 B。学习者选择 B，并独立指出“公式结构固定，每次只需代入计算”。
这说明其解释了固定公式的价值；不能据此记录为已经完成代码实践，或已掌握所有来源与
业务适用边界。导师补充：代入前仍要核对来源、单位、计费期间和收费规则是否适用。

## 规则与单位边界

新工具 prepare_billing 的参数只有 evidence_id 与 rule_quote，没有自由金额、单位或公式。
程序要求 rule_quote 去除首尾空白后等于所选证据块的完整正文，而不是正文中的一段引文。
正文必须完全匹配“月费 N 元，每次上门服务费 M 元”的受控语法；支持有限分隔符和空白，
金额非负、最多十二位整数和两位小数。不接受附加优惠、套餐、税费说明、标题、其他收费项
或不同业务单位；不能通过只截取前半句隐藏条件。
完整规则最多 400 字符，单项价格引文最多 200 字符。外围空白的等价比较通过后，
保存仍以实际块正文为准；超出复用的数值绑定契约限制时返回受控错误，不抛出内部验证异常。

程序复用原文数值绑定，保存块、文档、字符范围、逐字引文和十进制值。
monthly_fee 的单位固定为元/个月，visit_fee 固定为元/次；角色与单位由已验证的标准
语法确定，不接受模型传入的来源标签或单位声称。这是有限的单位兼容规则，不是单位换算。

只核对所选完整块，并不等于自动核对知识库中所有其他政策。其他块或文档可能还有优惠、
合同期限或适用限制。因此输出始终是“所选标准规则估算”，且需要用户明确确认该规则
适用于补充的同一计费期间。该确认不能被描述为系统已经验证了真实合同、实际账单或税务政策。

## 条件收集与执行

PendingTask 保留原问题与证据快照，新增有序 clarifications、billing_plan 和 billing_result。
原 clarification 仍表示当前正在等待的一个字段，兼容旧单字段任务。

受控流程依次补充：

- visit_count：同一计费期间的上门次数，0..9999，单位次。
- billing_months：同一计费期间的计费月数，1..12，单位个月。

收到“三次”时，程序依据当前待补字段将其保存为上门次数，而不是从聊天历史重新猜测。
随后继续询问月数，任务仍为 waiting_for_user；两项均补齐后才进入 ready。
即使原问题写了“全年”，也不自动把常数 12 当作用户已确认的计费月数。
每条确认输入保留独立的 request_id、raw_text、数值、单位及 user_message 来源。
首版不从初始问题自动提取条件，也不支持一条补充消息同时填写多个字段。

只有 ready 状态、mode=execute 且 confirm_billing_rule=true 时，才执行标准估算。
确认标志为严格布尔值，并参与该请求的幂等摘要。缺少确认返回冲突，不提交计算结果。
execute 消息的 content 只是审计说明，不是新的月份、次数、公式或收费规则输入。

执行时不调用模型，不使用 eval，没有扣费或其他外部写操作。
程序按固定三步做 Decimal 运算：月费乘月份、次费乘次数、两个小计相加。
两位小数费率乘整数不会引入除法舍入；显示按两位金额格式，保存可校验的十进制结果。
BillingResult 独立保存三步的输入引用、输入值、结果值、元单位及 program_calculation 来源，
同时保留收费计划、两个用户条件和确认请求编号。

## 状态、兼容性与持久化

只有受控 BillingResult 校验通过并原子提交后，会话才进入 completed。
旧 sourced_calculator 算术执行仍保持 ready，不因执行成功或确认标志静默升级为业务完成。
完成后，修改条件必须使用 new_task；不覆盖既有结果，新任务也不删除历史消息。
同一请求重试可以重放已提交的响应；相同 request_id 携带不同 payload 仍冲突。

继续复用 PostgreSQL JSONB、短事务、版本条件更新、消息幂等及知识库范围校验。
执行前和写回前核对证据快照；规则已变更、状态损坏或并发版本冲突时，不保存不可信结果。
事务外的模型准备与数据库提交分开，仍不承诺模型调用 exactly-once。
没有引入 Redis、通用工作流框架或新的独立业务表。

迁移 20261011_0007 仅放宽 conversations 的 status 与 task_status 检查约束，允许 completed。
旧会话状态、消息和任务不重写。只要当前存在标准计费状态，或历史响应中存在计费计划/
结果，降级就明确拒绝；即使 new_task 已替换当前任务，也不能抹去不兼容的计费历史。
没有 confirm_billing_rule=true 的旧请求保留原摘要算法和历史响应可读性。

## 验证与不解决的问题

验证应覆盖严格规则绑定、不能截断附加条件、伪造费率/单位/来源、月份范围、原消息回验、
固定三步与结果一致性。独立 PostgreSQL 验证逐项恢复、明确确认、重放、并发、原文变化、
状态损坏、旧任务兼容以及迁移拒绝不兼容降级。
最终完整后端回归 1273 项通过、无跳过（523.88 秒），新增 139 项；纯程序专项 91 项、
新计费会话专项 48 项通过，使用独立测试库和模拟模型。完整经过与本机正常迁移见学习记录，
不能把测试数量换算为业务质量或项目完成比例。

本模块不解释任意收费文档，不处理优惠、套餐、百分比、税费、跨年累计、日费或单位换算。
“模型是否找到正确完整块并选择 prepare_billing”仍需真实模型调用与语义质量验收，
不能把模拟模型测试通过率称为真实任务成功率。它也不是长期记忆或完整通用工作流模块的完成标志。
