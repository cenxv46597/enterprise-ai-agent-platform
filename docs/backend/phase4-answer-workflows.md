# 阶段 4.6：知识问答检查点与显式失败恢复

日期：2026-10-12。固定两步工作流程序验收完成，学习者实践、逐题面试和真实语义质量仍待验收；下文区分实际运行结果与个人学习状态。

## 一、目标

将“限定知识库检索 → 基于证据生成并校验引用”变成能保存进度的问答任务。
检索检查点已成功保存、生成发生超时时，新的请求可以核对旧证据后继续生成，不重复生成问题向量和检索。
这是独立的 `answer-workflows` 入口，不改写原有 `/answers`、`/agent-runs`、会话和计费契约。

本轮不恢复任意 Agent 决策、工具循环或计费步骤，不加入删除、审批、身份认证、后台队列、MCP 搜索、重排或答复偏好。

## 二、原因

学习者选择 B：保存已完成的检索步骤与证据，恢复时只继续后续步骤，并独立解释重复操作浪费时间和 token。
核心方向合理；费用需精确区分：数据库查来源本身不消耗模型 token，查询向量可能产生向量服务用量，生成回答可能产生生成服务用量，是否收费取决于配置的服务。
复用合法检查点减少重复检索与向量调用，但生成超时之后重试仍可能重复付费，不能承诺全部费用恰好一次。

此前会话状态保存“在等待用户补什么”，短期记忆给决策器有限近期对话；本模块保存“程序执行到哪一步”。
把聊天保存在数据库并不自动获得步骤恢复，把结果存在内存也无法供新应用实例继续使用。

## 三、概念

- **检查点：** 本步骤已完成的持久状态。保存已经选入生成预算的完整原文与来源，不只保存“检索成功”标记。
- **当前状态：** 工作流现在处于 `pending/running/failed/completed`，下一步为 `retrieve/generate/done`。
- **执行尝试：** 一次显式执行请求及其终态回执；最多五次，不等同于五次模型调用。
- **请求重放：** 已结束的相同执行请求返回保存的旧回执，不再次执行。新恢复必须使用新的请求编号和当前版本。
- **领取执行权：** 模型调用前，在短事务中把当前任务变为 `running`，保存请求编号、递增版本和租约。
- **写回隔离（fencing）：** 保存检查点或结果前核对同一个执行编号、版本和未过期租约。旧执行者不能覆盖新执行者的结果。

租约不是身份授权；900 秒表示该执行权的有效期，不是数据保存期限、模型 HTTP 超时或取消承诺。
目前不续租、不自动恢复、不按时间删除工作流；正常请求同步执行，进程消失后由调用方显式恢复。

## 四、设计

### 方案比较与当前选择

**A：整条任务重跑。** 状态少，实现简单，但生成失败后仍重复检索与向量调用，结果也可能因资料变化而不同。
**B：保存检查点。** 多出状态和恢复规则，但能复用已完成工作；旧证据必须再查数据库。本轮按学习者选择采用 B。

**只有最终 CAS 写回**可以挡住结果覆盖，却可能让两个首次请求都先调用模型，最后只有一个保存成功。
**执行前领取 + 每次写回核对执行权**可以让未过期 `running` 请求明确拒绝竞争，并阻止接管后的旧执行者写回。
本轮选择后者，网络请求仍在事务外，不持有数据库行锁等待模型。

**固定 Python 服务**便于复用现有检索和回答函数，两个步骤、明确状态适合当前规模。
**通用工作流框架**适合更多动态分支、后台调度和复杂恢复，但需要额外运行模型和维护能力。
本轮不引入 LangGraph、Redis 或任务队列；若流程复杂到需要这些能力，再以实际需求比较。
完整决策见 [ADR 0024](../adr/0024-checkpointed-answer-workflows.md)。

### 保存什么，如何限定范围

`answer_workflows` 保存原问题、创建请求摘要、知识库、策略、冻结字符预算、版本、状态、下一步、执行权、检查点和最终回答。
`answer_workflow_attempts` 保存请求摘要、尝试编号、状态与不可变终态回执；唯一约束分别限制创建编号和执行编号的作用域。
知识库仍关联工作空间，路径检查不等于已经有公司身份认证或资源授权。

首版仅本地 `vector/hybrid` 检索，固定 `top_k=5`。
创建时冻结 `min(EAAP_GENERATION_MAX_CONTEXT_CHARACTERS, 12000)`，恢复时不因后续配置变动偷偷改用更大的证据集合。
检查点保存按排名、字符预算选择的完整块，不截断；最多五块、正文总量 12000 字符、应用层 JSON 序列化不超过 100000 UTF-8 字节，禁止重复块。
正文同时必须不超过该任务创建时冻结的预算，不能仅因为小于全局 12000 就通过。
这些是程序输入限制，不等于服务商 token 上限或数据库恶意数据的解码前内存隔离。

来源核对检查工作空间、知识库、策略、块及文档身份、文档名、块编号、完整正文、字符范围、`ready` 状态与非空向量。
保存检查点、生成前和最终落库前都重新查询当前数据；合法 UUID 或以前核对成功都不能替代本次核对。
原文改变、块移库、删除或坏检查点将清除检查点，返回不可直接重试的固定失败，需要新建工作流，不静默重新检索或继续使用旧材料。
本轮核对的是检查点选中证据，不是整个知识库的版本；新增别的资料不会自动让旧检查点失效或重新召回。
恢复承接的是原任务的证据集合，不承诺它仍是新资料加入后最相关的集合；若要按最新资料重新检索，应新建任务。
检索距离与排名仍只是检索元数据，不是答案语义支持度或真实质量成绩。

空检查点 `hits=[]` 是合法结果：正常弃答并完成，不调用生成服务。若有候选但没有完整块能装入预算，属于 `context_limit` 故障，不伪装成正常弃答。

### 恢复、并发和旧回执

已捕获的向量/生成超时、可恢复配置或服务故障保存 `failed` 回执；调用方读取当前状态，确认 `retryable` 后，以新编号和当前版本执行。
有合法检查点时从 `generate` 开始；没有检查点则从 `retrieve` 开始。最多五次，达到上限后仍能读取当前状态和重放已有回执。

未过期 `running` 拒绝其他执行。崩溃留下的 `running` 不自动变成 `failed`，租约到期后仍需新请求编号、当前版本和 `recover_interrupted=true` 显式接管。
接管保存旧尝试的 `interrupted` 回执，再领取新执行权；旧执行者即使晚到也不能保存检查点、成功结果或失败状态。
来源共享锁也可能等待，所以核对原文取得锁之后再次检查租约，而不是只依赖等待前的有效结论。
租约判断在取得任务行锁后读取数据库当前时间 `clock_timestamp()`，避免把等待锁之前的事务开始时间当成此刻。
PostgreSQL 的 `CURRENT_TIMESTAMP/now()` 固定于事务开始，`clock_timestamp()` 表示调用时的实际时间，见 [PostgreSQL 17 日期函数说明](https://www.postgresql.org/docs/17/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)。

相同执行编号和完整相同 payload（包含 `expected_version`、`recover_interrupted`）只返回旧回执；同编号换 payload 返回 `409`。
例如第一次超时、第二次恢复成功后，重放第一次仍会得到第一次的失败快照，不表示工作流现在又失败了；当前状态通过 GET 查询。
创建请求复用则返回该资源的当前状态，不是创建时的不可变回执，两种接口不要混淆。

外部模型成功、程序在落库前崩溃时，服务商可能已经计费，而数据库没有最终回执。
接管后重新生成可能重复调用；执行权和请求重放保证平台写回边界，不能保证外部服务的费用 exactly-once。
租约不保证杀掉旧请求、旧网络调用或提供方工作，也不代替外部幂等协议。

## 五、实现

代码导航：

- `backend/app/workflows/contracts.py`：请求、检查点、当前状态与执行回执契约。
- `backend/app/workflows/service.py`：短事务领取、来源核对、保存检查点、生成与终态写回。
- `backend/app/api/answer_workflows.py`：创建、读取和显式执行入口。
- `backend/app/db/models.py`：两张工作流表和约束。
- `backend/alembic/versions/20261012_0009_answer_workflows.py`：0008 → 0009 的新增迁移。
- `backend/tests/test_answer_workflows.py`：真实独立数据库与模型替身故障场景。

知识库资源路径下新增三个端点：

1. `POST /answer-workflows`，创建只保存 `pending`，不检索或生成。
2. `GET /answer-workflows/{workflow_id}`，读取当前状态。
3. `POST /answer-workflows/{workflow_id}/execute`，显式同步执行或重放。

创建示例：

```json
{"request_id":"由调用方新生成的UUID","question":"服务如何恢复？","strategy":"vector"}
```

执行示例（使用 GET 返回的版本，不照抄旧值）：

```json
{"request_id":"本次执行的新UUID","expected_version":0,"recover_interrupted":false}
```

示例中的中文说明不是可发送的 UUID；可用 Python `uuid.uuid4()` 生成。
创建默认 `vector`；请求严格拒绝额外字段和布尔/字符串版本，不接收任意步骤、MCP 后端、重排或偏好。
成功、正常弃答及被保存的业务执行故障通过 `200` 回执的状态、`error_code` 和 `retryable` 区分；资源不匹配 `404`，冲突 `409`，参数错误 `422`，数据库操作失败 `503`。
HTTP `200` 不意味着执行成功，调用方必须检查回执。
回执只保存固定故障码，不保存第三方原始异常、密钥、连接地址或堆栈。
数据库提交可能已成功但确认丢失；此类错误不尝试用旧版本再写“失败”，由 API 返回固定 `503`，调用方先 GET，再决定原请求重放或过期显式恢复。
execute 复用已有即时构造的 `EmbeddingDep`：即使恢复合法检查点或重放旧回执不发向量 HTTP 请求，接口仍需能构造基本向量配置；地址/密钥等配置缺失可在领取前返回 `503`，不产生持久 failed 回执。create 与 GET 不依赖该提供方。
因此本模块支持“已有配置、向量服务暂时不可用时复用检查点”，不能称为完全摆脱向量配置；零模型请求也不等于无需配置。

迁移新增表，不改写已有知识、会话或偏好数据。0009 降级在同一事务先锁两表，再检查任何数据，包括仅创建的 `pending`；非空就拒绝删表，不能把未执行任务当成无价值历史。
测试库迁移通过不等于本机应用库已经升级。本轮本机应用库已另外按正常流程由 0008 升至 0009，七张旧表计数前后相同：workspaces=2、knowledge_bases=2、documents=5、chunks=34、conversations=0、conversation_turns=0、answer_preferences=0；新 answer_workflows=0、answer_workflow_attempts=0，compare_metadata=[]。
没有重建卷、删除资料或在应用库运行数据库测试。
