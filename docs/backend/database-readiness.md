# 应用数据库就绪检查：2026-10-18

## 目标与选择

数据库容器健康，不等于后端能用自己的配置连接数据库。本小步增加一个可由部署探针调用的只读入口，
区分进程响应与数据库连通性；不扩展网页业务、不恢复暂缓的真实检索任务。

学习者确认方案A：保留 `/health`，新增 `/ready`。方案B是让原 `/health` 同时检查数据库；
A保留已有接口含义，也避免把数据库故障混同为进程故障。方案确认不记为独立完整设计理由。

## 实现与公开契约

- `GET /health` 保留200及 `{"status":"ok"}`，不访问数据库。
- `GET /ready` 成功返回200及 `{"status":"ready","database":"ok"}`。
- 配置加载、连接、查询或资源释放失败，返回503及 `{"status":"not_ready","database":"unavailable"}`。
- 两种就绪响应都带 `Cache-Control: no-store`。接口不要求登录、不签发Cookie，
  不返回连接地址、用户名、密码、数据库版本或原始异常。

系统路由继续由 `app.main` 注册。`app.db.readiness.database_is_ready` 把配置读取到连接清理
放在同一失败边界内，避免生成器依赖在进入路由前失败而漏过异常处理。

探测使用应用 `Settings().database_url`，仅支持 `postgresql+psycopg`，
每次创建独立 `NullPool` 引擎，不使用或调整已有业务连接池。
显式设置连接尝试超时3秒、单条语句超时2秒、锁等待超时1秒、默认只读事务。
执行 `SELECT 1` 并确认值为1；连接上下文结束，随后释放引擎，无业务写入、迁移或模型调用。
SQLAlchemy连接初始化本身还可能执行只读元数据查询，不能把它描述为总共只有一条网络SQL。

这些超时不是整个HTTP请求的硬性总时限，DNS、多主机连接等可能增加耗时。
独立连接探测成功也不证明业务连接池没有耗尽。

## 能证明什么

200只说明当次应用配置加载成功，所指数据库可建立新连接并完成常量查询。
不能据此认定业务上选对了数据库、0010迁移完成、业务表存在、表权限或业务数据正确，
也不能证明JWT/Cookie登录、真实网页、pgvector检索、生成模型或整个系统已验收。
503同样不等于后端进程已停止，应结合 `/health` 区分。

日常库0010与既有账号owner关系不改，ADR0030继续有效；真实候选检索、模型调用和实际等待Cookie到期仍暂缓。
没有启动前后端供学习者实际操作，不把TestClient当作本人浏览器验收。
