# HTTP访问摘要的时间与运行来源：2026-10-19

## 改了什么、为什么改

既有访问摘要可按trace_id定位一次HTTP调用，但缺少时间、服务和环境，难以筛选某个时段、
区分测试与生产日志。本步只扩展摘要字段，不接入日志采集平台或改动业务执行流程。

新增字段：

- `recorded_at`：应用在本次ASGI调用退出时尝试记录摘要的UTC时间，ISO 8601、毫秒精度、Z结尾。
  它不是请求到达时间、数据库提交时间或工作流完成时间，也不是日志平台实际收到的时间。
  未捕获异常时，此记录还可能先于外层ServerErrorMiddleware实际发送500响应。
- `service`：固定为 `eaap-api`，标识本后端服务，不取可自由填写的app_name或入站头。
- `environment`：由main将已校验的Settings.app_env传入，每个中间件实例单独保存；
  仅允许local/test/production。直接构造时默认local；无效值在初始化时拒绝，错误不回显输入。

原七字段event、trace_id、method、route、status_code、elapsed_ms、outcome保持语义，
最终一行JSON有十字段。时间采集、字段组装和输出均在尽力记录的异常保护内；失败可能丢日志，
不会替换成功响应或原业务异常。非HTTP调用仍透传，不采时间或生成摘要。

## 设计取舍与实际场景

选择统一UTC记录时间，而非每台机器按本地时区输出，方便后续集中查询；用户界面未来可按需转时区。
`elapsed_ms`仍由perf_counter计算，它是测量时间间隔的单调时钟；系统时间用于表示日期和时刻，
可能因校时变化，不能简单用两个系统时间相减替代请求耗时。

不把environment放入全局logger/filter，避免同一进程的不同app覆盖彼此配置。
service与environment只能区分服务和环境，不能定位同环境内的具体实例；本步不增加新的实例编号。
多机系统时间也不能保证严格全局排序，未来集中采集仍需时钟治理、存储与查询方案。

实际排障可以先按production、eaap-api和时间窗口缩小范围，再用页面提供的trace_id找到该次请求摘要。
仅靠这些字段仍不能判断失败根因、外部模型调用次数、费用或数据库最终结果。
日志仍输出stderr、无文件或集中保存保证；当前级别仍是INFO，旧业务与Uvicorn异常日志未整体治理。
