# 引文来源按目标文本块读取

2026-10-22。接续[完整来源段落查看](../frontend/frontend-answer-source.md)已结束的一个实践和两题讨论；本人要求进入下一步，导师将这条来源读取链路改为按目标块获取，保持知识库问答主线。主体设计、代码、测试与运行均由导师完成，本轮教学实践和面试尚未开展，不预记本人独立实现或掌握。

## 业务目标与完成条件

用户已经获得回答，点击某条引文只需查看它所在的一个完整文本块。原实现先读取文档详情，再获取该文档全部块、在前端挑出目标块。文档越长，未展示正文的传输越多。

本轮完成条件是：保留手动点击和文档最新状态核对，第二个GET仅返回指定块；错误父级路径、非成员和不存在的块不能返回正文；旧块列表继续服务切块页及已有调用者。失败仍只影响来源区，保留原答案，不重新检索或生成。

## 方案与兼容

新增资源接口：

```text
GET /api/v1/workspaces/{workspace_id}/knowledge-bases/{knowledge_base_id}/documents/{document_id}/chunks/{chunk_id}
```

相比继续取全列表再筛选，后端可在数据库中按目标ID定位，减少无关正文传输。相比给旧列表加过滤参数，独立资源路径能明确表达“返回一个对象或404”，保留旧列表的数组响应与空数组语义，避免旧CLI和页面适配新返回类型。没有新增依赖、数据库迁移或索引，现有块主键足够定位。

[后端路由](../../backend/app/api/documents.py)沿用真实登录和工作区成员依赖。业务SELECT连接块、文档和知识库，同时约束四层ID；不能仅凭知道块ID读取，也不能因用户恰好拥有两个库权限就忽略URL归属。范围不匹配统一返回404“文本块不存在”，非成员在成员查询阶段即被拒绝。

仅选择公开的六列：id、document_id、chunk_index、content、start_char、end_char，不加载或返回embedding。一次成功请求包含既有成员查询及一条业务JOIN查询。通用单块读取允许parsed文档，和已有列表一致；引用问答另在文档GET中要求ready，不把两种职责混合。

## 前端链路和保证边界

[API客户端](../../frontend/src/api.ts)新增getDocumentChunk，要求200对象、精确块ID和父文档、正整数块号、有效字符范围及完整正文。共用单块解析器按Unicode码点计算长度，允许第2块以后及非零起点；旧列表仍另行检查连续块号、首块零起点、重复ID、顺序/重叠和总字符上限，未放宽旧契约。

[来源核验](../../frontend/src/answer-source-api.ts)改为“文档详情GET → 指定块GET”，不回退列表请求。原名称/归属/ready、块号、绝对字符位置和引文逐字核对保留；取消、401、实际失败GET编号及迟到响应隔离仍由原机制处理。页面仍显示完整目标块并标亮引文，失败保留原答案供手动重读来源。

本轮减少无关块的读取，不减少两个前端GET的数量；没有延迟或吞吐基准，不能声称加速多少倍。完整来源仍只指一个块，不能证明其他引文、整块生成时快照、两个GET原子一致或答案语义正确。已有工作流保存答案需要核验全部来源，继续使用原列表流程，没有顺带迁移。
