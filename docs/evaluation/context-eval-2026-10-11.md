# 上下文证据覆盖评测：2026-10-11

## 目标与执行范围

检索返回了正确证据，仍可能因上下文预算而没有把它交给回答模型。本模块分别记录检索覆盖和按业务规则选中的上下文覆盖，定位两个环节之间的证据损失。

本次离线回放[昨天保存的真实检索结果](retrieval-eval-2026-10-10.json)：4 份公开虚构文档、29 个候选块、6 个固定问题。4 道正例共标注 5 条必需证据，2 道负例不计覆盖分。没有访问数据库、生成新向量或调用回答模型。选中列表代表复用现有规则后拟送入模型的证据，本次没有实际发送这些上下文。

## 数据流与实现

固定题集和公开原文 → 校验快照身份及全部返回块 → 分别取前 5 和前 10 → 用正文预算选择完整块 → 再检查黄金证据覆盖 → 保存报告。

- `backend/app/knowledge/context.py` 的 `select_context` 是共用的纯函数；按排名保留完整块，放不下的块跳过，并继续尝试后面的块。
- 正式 `answer_knowledge_base` 和离线 `evaluate_context` 调用同一函数。原答案流程、默认预算、接口错误映射和引用构造保持原有行为。
- `SelectedSource` 同时记录原检索排名和重新编号的 `source_id`。选中列表的第 2 条可能来自检索第 3 条，引用不能继续沿用原排名。
- `ContextEvaluation` 分别保存选择前后的 `CaseEvaluation`，并记录 `lost_evidence_count`、使用字符数、排除块数和选择状态。
- 选择过程只看排名和正文长度，不用黄金答案挑块。黄金证据仅用于选择后的评测，防止答案泄漏造成假成绩。

全部候选均先与公开原文及字符范围核对，包括未进入前 K 或被预算排除的块。原始检索报告、题集和语料不被改写；快照摘要采用规范 JSON，避免 Git 的换行规范化导致跨机器身份不一致。

## 三种预算的实际回放结果

每道题检查 2 种候选量和 3 种预算，共 36 次离线选择。对于前 5 和前 10，结果相同：

- **600 字符：** 检索覆盖 5/5 条必需证据，上下文覆盖 2/5；2/4 道正例找齐证据，选择阶段丢失 3 条。
- **2000 字符：** 检索覆盖 5/5，上下文覆盖 4/5；3/4 道正例找齐证据，选择阶段丢失 1 条。
- **12000 字符：** 检索和上下文均覆盖 5/5；4/4 道正例找齐证据，无选择阶段损失。

12000 是代码默认正文预算，实际环境配置可以覆盖它。本次较小预算是故障练习，不表示默认配置下已发生同样损失。扩大检索候选量也未解决这组样本中的预算损失，不能因此认定在其他问题上扩大候选量没有作用。

原始统计、来源位置和选择记录见 [JSON 报告](context-eval-2026-10-11.json)。两个负例仍为 `null` 分数，不能把空黄金列表计为满分，也不能从这次回放推断模型会合理弃答。

## 方案取舍

整块选择保留引用位置和上下文完整性，容易解释与测试，但可能留下未用预算，或保留主题相关而没有答案的高排名块。

截断可以提高预算利用率，但可能切掉“健康检查通过后”等条件、顺序或关键步骤，需要同步维护正文与引用范围。当前先评测既有整块规则，未新增截断、重排、自动续检或评分模型，详见 [ADR 0008](../adr/0008-context-evidence-coverage.md)。

## 如何复现

不需要 `.env`、数据库或 API 密钥。从仓库根目录运行：

```powershell
.\.venv\Scripts\python.exe backend/scripts/evaluate_context.py --plan
.\.venv\Scripts\python.exe backend/scripts/evaluate_context.py --write-report --report docs/evaluation/context-eval-local.json
```

输出路径须在 `docs/evaluation` 内。已有报告不被覆盖；需要比较其他预算时选择新文件名：

```powershell
.\.venv\Scripts\python.exe backend/scripts/evaluate_context.py --write-report --budgets 600 1000 12000 --top-k 5 --report docs/evaluation/context-eval-practice.json
.\.venv\Scripts\python.exe -m pytest backend/tests/test_context_evaluation.py backend/tests/test_context_evaluation_cli.py -q
```

共享函数抽取后完整后端回归 **482 项通过、无跳过，165.37 秒**，使用独立 PostgreSQL/pgvector 测试库和受控模型。之后补充跨换行身份测试，新模块 **30 项专项测试全部通过**。两次验证分别记录，不能把重跑专项的数量加到完整回归数中。

## 结果不能证明什么

这里测的是预标注必需证据覆盖，不是完整 Recall、Precision 或真实回答忠实性。字符预算也不是 token 数，更没有包含系统提示词、问题、JSON 格式和模型输出预算。本模块没有测量模型延迟、token 或费用，默认预算覆盖全部证据仍不保证答案正确。

## 小实践与后续面试

打开 `test_retrieval_hit_can_be_lost_from_generation_context_under_budget`，先预测两个 500 字符块与一个 80 字符块在预算 600 下的选择结果，再对照原检索排名和来源编号。把预算改成 1000，自己预测覆盖数和排除块数，并调整断言验证；无需调用模型。

接下来逐题讨论：检索命中为何仍可能丢失回答证据；直接截断段落可能破坏哪些条件；候选扩大而覆盖不变时，怎样决定是否需要重排。实践与独立解释能力需要学习者亲自完成后记录，不能由代码通过代替。
