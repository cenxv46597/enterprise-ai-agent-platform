# 当前知识库文档状态筛选

2026-10-23，接续文件名查找与手动翻页。起点`6d73207`，此前浏览器模块一个实践与两道讨论已收尾。
本次完成一个业务闭环：员工查找“报销”资料时，同时选择“解析失败”等处理状态，再对符合两项条件的文档翻页。

## 业务范围与取舍

沿用已有文档列表及后端可选`status`，只接网页，不新增接口、数据库迁移或模型任务。
文件名与处理状态取交集：同一份文档必须满足全部已应用的条件，而非分别符合任意一项即可。
可选择全部状态、已上传、解析中、已解析、可检索、解析失败；默认全部，兼容原列表行为。
这能定位需要处理的旧资料，也能查看已可检索资料；筛选不会启动解析或修复失败文档。

比较选择状态即请求，或与文件名统一点击“查找”：本次沿用后者。
两项草稿可以一起编辑，点击查找后同时生效并回首页，避免新状态与尚未提交的文件名被意外混用。
“清除查找”同时清除两项条件和草稿，读取无条件首页。
选择状态只改草稿，页面另显示已应用的文件名与文档状态，使列表实际范围可见。

## 调用与恢复

请求仍为当前空间/知识库的`GET .../documents`。
例如`?limit=20&offset=20&filename_query=报销&status=failed`表示符合报销文件名且解析失败结果的第二页，
不是先取所有文档第二页再在浏览器过滤。真实后端在成员/父级校验后先约束空间、知识库、状态及文件名，再排序分页。
省略`status`代表全部状态；网页内部的`all`不发送给后端。
`listDocuments`在末尾追加默认参数，原有调用无需改写；非法状态在请求前拒绝。

App保存两项草稿、两项已应用条件和目标offset。刷新、手动重试、翻页、详情返回、其他库内子页返回及上传后刷新，
都使用已应用条件与目标页，并保留未提交草稿。重新进入知识库、返回空间、401、退出成功及原登录期限到期清理条件。
继续复用单请求控制、取消信号与操作序号，取消后的旧响应不能覆盖新上下文。

前端继续整批校验最多20条、文档归属、ID、文件名及已知状态；指定某状态时，若响应混入其他状态则整页拒绝，
不通过浏览器悄悄丢掉不匹配行来掩盖契约问题。错误使用已有安全提示，不展示任意服务端字段。
首页无匹配与空知识库区分，空尾页仍可回退，请求失败不显示为空结果；页内计数始终只统计当前页。

新上传结果独立于筛选列表。例如当前应用`ready`，新文件为`parsed`时列表可不包含它，
但已确认上传卡仍显示，并可按新文档ID进入处理；列表刷新503也不能撤销上传确认或自动再次上传。

## 范围边界

查找只影响文档管理列表。引用问答仍按原当前整个知识库执行，不只使用当前文件名、状态或这20条结果。
页面提示明确这一点；本轮没有改变检索/问答请求、证据规则、ready含义或答案质量保证。
`parsed`仍不保证已切块或已向量化，`ready`仍不保证任何问题都有足够证据。

没有增加总数、游标或数据快照；满20条只表示允许尝试下一页，不能证明还有记录。
并发处理可能改变文档状态，offset跨页仍不保证不重不漏；没有自动轮询，也不持久保存筛选条件。
整页刷新仍只恢复登录并回工作空间，不构成服务器历史。
