# 引用问答手动选择候选段落上限

2026-10-23，起点`f8b04b1`之后的学习记录`efd2e59`及零候选提示模块。零候选提示的练习尚未作答，
本人直接要求按正常节奏进入下一模块；不把未答题记为已掌握。本模块方案、代码、测试由导师完成，
本人实践与面试讨论待先讲解后逐题进行。

## 场景与方案

员工本次问答弃答，可能希望手动扩大检索候选，再判断能否找到足够证据。后端`/answers`已有严格
`top_k`范围1到20；之前网页固定3。本轮只在独立引用问答页提供“最多3段/最多5段”，默认3，
不改变独立检索页、会话、工作流或后端算法，也不自动重试、重排或调用真实模型。

比较直接把所有请求改为5与手动选择3/5：前者改变既有基线，也可能增加处理时间与费用；
后者保留旧行为，让使用者明确决定何时提交新请求。因此采用3/5两档，不开放1到20任意输入。
切换下拉框不发请求；点击“生成回答”才向当前知识库发送一次`POST /answers`，携带所选
`top_k`、问题、检索方式与`rerank:false`。API旧调用默认3，非法数量在fetch前拒绝。

`top_k`是检索候选**上限**，不是实际返回数、送进生成上下文的块数或最终引文数。
后端按上下文字符预算选完整块，可能跳过超预算候选；模型可只引用其中一部分，也可能弃答。
增加上限不保证回答质量或证据充分；是否改善需要固定问题与标注答案评测，本轮没有该证据。

## 提交快照与导出

页面把本次提交的`top_k`与问题、方式和已核验答案放在同一个confirmed结果中。
后续修改草稿不改旧结果，新提交先清旧结果；来源成功/失败/关闭与导出提示更新保留原上限。
返回、退出、到期和重进问答页恢复默认3。来源逐文档核验、正常弃答与故障区分保持原规则。

TXT白名单增加“本次提交的候选上限”；导出只读confirmed快照，不读取当前选择，也不新发HTTP。
缺失/非法上限在创建Blob/下载链接之前拒绝，不猜默认3。提交参数仍非服务端执行回执，
TXT不是服务器历史；“已请求浏览器下载”不证明文件落盘。正文没有自动隐私脱敏。
