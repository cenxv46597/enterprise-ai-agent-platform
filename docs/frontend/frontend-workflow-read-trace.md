# 工作流创建页只读排错编号：2026-10-20

接续[历史页保存答案编号](frontend-workflow-saved-answer-trace.md)，本步补齐创建页的两个只读动作：读取当前工作流状态，以及查看已保存答案。用户明确选择本范围，主体实现与测试由导师完成，无本人代码修改；教学、小实践与面试另按实际参与记录。

## 业务目标与完成条件

用户在创建页读取失败时，能把页面编号提供给维护者，关联实际失败的 HTTP 安全访问摘要。编号属于这次 HTTP 调用，不是工作流执行编号、鉴权依据或幂等凭证，不证明模型调用次数或保存结果。

完成条件：两个提示区展示各自失败 GET 的合法 UUID4；重读清旧、取消/返回/退出/到期及迟到响应不串入；失败清正文及完成读取依据，仍需重读状态后才能查看答案；恢复条件与完整来源核验保持正确。

## 设计与实现

- 复用已有 API 的 `ApiError.traceId`、UUID4 校验与来源错误包装，不改 API/后端。状态 GET 与答案工作流/文档/文本块 GET 都只取实际失败响应编号。
- `readNotice`、`savedAnswerNotice` 从字符串改为 `{message, traceId}` 或 `null`。相比全局最近编号，提示自身携带编号可明确请求归属；空提示用 `null`，保持既有恢复门控的真假判断。
- 从历史页提取 [WorkflowReadNotice.tsx](../../frontend/src/WorkflowReadNotice.tsx) 的类型与 `ReadNotice`，两页共用。此前本人补的“反馈问题时请提供此编号”用途文案原样保留，历史页行为不扩大。
- 状态成功后读到变化，仅显示原“暂停写入”说明，编号为 null。成功响应后坏 JSON、快照或原文核验不符，无响应、网络、取消及超时都不补造编号。
- 重读状态清两处旧提示和保存答案；查看答案清旧答案提示，失败仍清快照/正文。取消提示不保留编号；退出尝试立即清两区编号，退出失败不恢复旧编号或显示退出响应编号。
- 保留请求序号/AbortController 隔离迟到结果，401回登录。恢复条件仍要求本页可信失败回执与当前一致读取，没有读取成功不能恢复。

保存答案仍核对全部选中来源，包括未引用候选块的完整原文、身份和字符位置；多个 GET 不是原子快照，不代表语义质量审核。没有全知识库重检索、新模型调用或未知写请求精确回执。

创建、执行、恢复 POST 的编号展示不在本步范围，没有自动重试、轮询或恢复，也没有新增接口、依赖、数据库迁移或浏览器持久化。
