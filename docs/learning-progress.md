### 来源追溯设计：第一次回答与反馈

学习者提出：文档名称用于来源展示，文档内容用于定位段落，文件目录用于找回原文件。

反馈：三个业务用途合理。现有 `Document` 已保存原文件名和存储键，每次上传有独立 UUID；文本块可通过文档 ID 关联这些信息。重复文件名不能唯一标识文档，重复文本也不能唯一确定原文中的出现位置。文件目录属于服务端存储信息，当前接口没有把它暴露给用户。

比较：每个文本块复制文件名和路径可以减少一次关联查询，但会重复保存信息；通过文档 ID 关联现有文档表更适合当前项目，代价是查询来源时需要关联。原文位置的字段设计留给下一次场景判断。

当时布置的实践：使用同一份文档中两处完全相同的文本，检验设计是否能区分其来源位置；该测试现已实现，见下一次回答记录。

### 来源追溯设计：第二次回答与代码验证

学习者提出：相同句子第一次出现编号为 1，第二次为 2，以区分其位置。

反馈：增加顺序信息能区分重复出现；实现时对所有文本块连续编号，不需要先识别重复句子。编号表达顺序，字符起止位置用于直接取回原文，二者用途不同。

重复句子的测试现已实现：原文为两次连续的“重启后恢复服务。”，块内容相同，但编号为 1、2，字符范围为 `[0, 8)`、`[8, 16)`，且两块都满足 `原文[start_char:end_char] == content`。

代码位于 `backend/app/knowledge/chunking.py`，测试位于 `backend/tests/test_chunking.py`。本轮只完成可独立运行的算法；持久化和上传接入待后续开发。设计取舍见 [ADR 0002](adr/0002-deterministic-text-chunks.md)。

学习者可在虚拟环境中运行 `python -m pytest backend/tests/test_chunking.py -q`，再用相同原文改变块长度、观察序号与内容的对应关系，并提交自己的判断。该练习只使用字符串，不依赖数据库。

### 重切块引用与 Python 断言练习

学习者判断旧编号无法继续可靠指向原来的完整句子，并正确解释：每次切分的字符数量发生了变化。书写测试时尝试使用 `if old_chunks == new_chunks`，当前需要补齐测试断言、比较运算符、列表下标和对象属性的用法。

本次将例子写成回归测试：块长度为 8 时，第 2 块内容为“重启后恢复服务。”；改为 12 后，第 2 块内容为“复服务。”。核心断言为 `assert old_chunks[1].content != new_chunks[1].content`。在原文不变的前提下，测试也验证旧字符范围仍能取回原来的完整句子。

`assert` 检查条件；条件成立时继续执行，不成立时抛出 `AssertionError`，由 pytest 报告失败。`==` 判断相等，`!=` 判断不相等，列表下标 `[1]` 表示第 2 个元素，`.content` 获取块内容。导师提供了这条断言，学习者独立写出断言的能力仍待下一次练习验证。
